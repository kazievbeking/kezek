# Архитектура и версии протокола

Runtime 1.1.0 использует модель назначений услуг сотрудникам без столов и протокол HTTP/Socket.IO v2. Control Plane остаётся на v1. Актуальные поля, совместимость, сохранение истории и переход описаны в EMPLOYEE-SERVICES.md. Упоминания столов и Runtime v1 ниже относятся к предыдущей версии.

## Независимые приложения

Control Plane и Runtime используют **разные Prisma clients, разные URL и базы PostgreSQL**, отдельные backend-процессы и сборки frontend. В обычном меню Runtime нет ссылки на панель владельца. Сессии имеют разные cookie (`kezek_control`, `kezek_runtime`); роли Runtime не авторизуют запросы в Control Plane. У Runtime нет публичного API создания владельца платформы.

Control Plane хранит заказчиков, филиалы, установки, хеши регистрационных токенов, подписываемые команды, согласованные последние сведения и релизы. Runtime хранит реальные учётные записи и назначения, устройства и сессии, услуги/столы, смены/паузы, талоны/вызовы/интервалы/передачи, импорт, аудит и состояние обновлений.

Одна установка Runtime может обслуживать несколько компаний/филиалов. Отдельные локальные установки имеют свои базы и оперативные очереди. Общая консоль Control Plane показывает **последние известные сведения с временем синхронизации**; она не объединяет талоны из независимых баз. Админка компании видит только филиалы, реально присутствующие в данном Runtime.

## Доступ

- COMPANY_ADMIN: все филиалы своей компании.
- BRANCH_ADMIN: назначенные филиалы; управление сотрудниками STAFF в полностью доступной области. Нельзя повышать роль, редактировать администратора компании или назначать чужой филиал.
- STAFF: один или несколько назначенных филиалов, услуги и столы; текущая смена одна на пользователя.
- TERMINAL: снимок разрешённого филиала, выдача/печать.
- DISPLAY: только отображение и собственные настройки языка.
- WORKSTATION: отдельная регистрация компьютера; не заменяет вход сотрудника.

HTTP и WebSocket проверяют роль, companyId, branchId и активность сессии. Выбор филиала — `X-Branch-Id` / `auth.branchId`; подмена не даёт доступа. Роли и назначения заново проверяются внутри критических транзакций. Персональные сведения сотрудников не входят в снимки устройств; STAFF не получает чужие логины, email и назначения.

## Очередь

`transaction(companyId)` берёт shared advisory lock обслуживания установки и transaction-scoped lock компании. Это согласует команды разных клиентов и процессов в PostgreSQL. Разные компании не блокируют друг друга при обычной работе. Частичные уникальные индексы запрещают две открытые смены на стол/пользователя, два активных талона на стол/пользователя, два открытых запроса передачи и два открытых интервала одного талона. Составные внешние ключи защищают связи компании/филиала.

Ключ `Idempotency-Key` уникален для исполнителя; fingerprint включает филиал, действие и тело. В одной транзакции сохраняются результат, изменение очереди, аудит, версия филиала и outbox. Повтор ключа возвращает прежний результат; другое тело/филиал — конфликт. Неизвестный результат сохраняется в браузере до подтверждения.

Счётчик `(companyId,branchId,date,prefix)` увеличивается атомарно. Дата определяется часовым поясом компании с разрешённым переопределением филиала. UUID талона постоянен; полночь ничего не удаляет. FIFO выбирает самый ранний ожидающий талон разрешённых услуг стола/сотрудника.

WAITING → CALLED → SERVING → COMPLETED; активные талоны допускают отмену, CALLED — неявку. Передача — отдельная PENDING → ACCEPTED / REJECTED / CANCELLED / EXPIRED. До принятия назначение сохраняется. При принятии повторно проверяются свободный работающий получатель, филиал, стол и право на услугу; текущий интервал закрывается, создаётся новый вызов того же номера. Новый интервал начинается по действию получателя «Начать обслуживание».

## Синхронизация

По умолчанию **HTTP polling**: GET `/api/state?version=N`, обычно раз в 1,5 секунды. При той же версии возвращается `{unchanged:true,version}`. Совпадающие запросы не выполняются параллельно; ошибки увеличивают интервал до 15 секунд. Последний снимок помечается устаревшим при ошибке.

В WebSocket/Auto используются Socket.IO с авторизацией cookie, отдельными комнатами филиалов, heartbeat, jitter/backoff и полным снимком после reconnect. Auto переходит на обычный HTTP polling при недоступном WebSocket. Уведомления содержат только id, branchId, version, protocol и тип; дубликаты отсекаются версией, пропуск приводит к полному снимку. Команды всегда HTTP. Изменения могут приходить с задержкой polling-интервала; polling не называется мгновенным.

Outbox публикуется после commit и отмечается после emit; возможны дубликаты. Источник истины — БД. Для v1 используйте **один процесс API на установку Runtime**: горизонтальное масштабирование Socket.IO потребует общего адаптера/брокера. Наличие блокировок БД не заменяет брокер событий. Updater и bridge — отдельные задачи, а не второй API с отдельной очередью.

## Основные API

Runtime: `/api/login`, `/api/me`, `/api/password`, `/api/preferences`, `/api/enroll/preview`, `/api/enroll`, `/api/state`, `/api/commands`, `/api/admin/:entity`, `/api/import/*`, `/api/reports`, `/api/export/csv|xlsx`, `/api/updates/*`. Записывающие запросы после входа требуют `X-CSRF-Token`; секрет сессии HttpOnly. Ответы API и HTML не кешируются, Vite assets имеют content hash. `X-Kezek-Protocol` контролирует совместимость; по умолчанию текущая версия — 1.

Control Plane: `/api/login`, `/api/me`, `/api/state`, `/api/manage/companies|branches|installations|tokens|owners`, `/api/manage/revoke-token`, `/api/manage/remote`, `/api/releases`. Все изменения требуют сессии владельца и CSRF. `/api/bridge/sync` и `/api/bridge/ack` используют отдельный отзываемый секрет установки, хеш которого хранится в Control Plane.

Runtime `/api/setup` требует **секрет установщика из окружения плюс подписанный пакет**, проверяемый публичным ключом. Это не публичная регистрация владельца. `/api/bridge/command` принимает только подписанные, адресованные этой установке команды с журналированием и receipt-защитой от повторов. Приватный ключ владельца отсутствует у заказчика.
