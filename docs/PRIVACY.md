# Передача данных и удалённое администрирование

## Выбор режима

Режим задаётся явно при создании установки и подтверждается установщиком при импорте подписанного пакета:

- **managed**: передаются версия/установка и устройства (ID, компания/филиал, название, роль, активность, lastSeen, версия). Данные сотрудников не передаются ни в одном режиме и остаются в Runtime компании. Control Plane игнорирует поле employees от старых Runtime; ранее сохранённые списки удаляются новой миграцией.
- **isolated**: персональные сведения сотрудников и устройств не передаются. Control Plane получает ID, версию, режим, время последнего успешного контакта и технические version/status/updatedAt последних 10 обновлений. Талоны, отчёты и статистика остаются локально.

Обе стороны должны разрешать managed, иначе Control Plane отбрасывает персональную часть. Сериализация использует явный allowlist, а не копию ORM-объекта. **Пароли, хеши паролей, cookie, CSRF, секреты устройств, база и талоны не передаются ни в одном режиме.**

Локальный оператор может изменить политику через `node --env-file=.env --import tsx scripts/set-privacy.ts isolated` (или managed); действие аудируется. Пустые BRIDGE_URL/BRIDGE_TOKEN полностью отключают исходящий bridge. Изолированная установка может работать без внешней сети, используя подписанные файлы активации/обновления.

## Последнее известное состояние

Bridge пытается синхронизироваться примерно раз в 30 секунд, с ограниченным таймаутом. Его недоступность не участвует в выдаче, входе, вызове или обслуживании. Консоль показывает lastSync, режим и версию; отсутствие новых данных не означает мгновенную удалённую доступность. Списки устройств в managed — снимок на последнюю синхронизацию, не оперативная общая очередь. В isolated персональных списков нет. Раздела сотрудников в Control Plane нет; сотрудники управляются администратором компании в Runtime.

## Привилегированные команды

Владелец входит в отдельную Control Plane-сессию. Отзыв устройства/токена превращается в подписанную, адресованную установке команду с UUID. При доступном URL Runtime Control Plane пробует доставить её сразу; иначе хранит PENDING. После восстановления Runtime получает очередь и применяет её с receipt-защитой от повторов. Команды и их результат записываются в аудит с идентификатором владельца. Создание новых команд BLOCK_USER из Control Plane отключено; Runtime сохраняет поддержку уже подписанных команд протокола v1.

Регистрационный токен отзывается отдельно от уже выданных сессий устройств. Выключение новых подключений компании в Control Plane отзывает её регистрационные токены через тот же канал; уже работающая локальная очередь и устройства не выключаются из-за недоступности облака. Для полного отзыва конкретного устройства — отдельная команда. При изоляции команды не могут примениться мгновенно.

У Runtime нет универсального пароля владельца. Для полного административного доступа оператор Runtime явно включает `ALLOW_OWNER_ACCESS=true`. В Control Plane → «Установки» владелец выбирает компанию и скачивает подписанное одноразовое разрешение. Его нужно загрузить на доступном адресе Runtime `/owner-access` в течение 5 минут. Разрешение адресовано одной установке и компании; повторное использование запрещено. Административная HttpOnly-сессия действует 30 минут и прекращается при выключении настройки. Доступ к настройкам, сотрудникам и отчётам равен COMPANY_ADMIN, но команды обслуживания очереди от имени владельца запрещены. В журнале Runtime действия отмечаются отдельным `owner:<id>`, без подмены сотрудника. Выдача разрешения записывается в Control Plane, вход и изменения — в Runtime. Удалённый shell и автоматический туннель не предоставляются.

Такой вход возможен и в isolated только при разрешённом сетевом доступе к Runtime. Он не включает фоновую отправку персональных данных: просмотр выполняется непосредственно на Runtime. Если установка не доступна по сети, Control Plane не обещает мгновенного доступа; нужен одобренный заказчиком VPN/локальное подключение.

## Ограничения браузерной привязки

Сессия HttpOnly затрудняет доступ JavaScript к секрету, но не защищает от администратора ОС, копирования профиля или доступа к серверу заказчика. Исходники локального сервера технически доступны его администратору. Система не обещает невозможность копирования приложения или аппаратную неклонируемость браузера. Используйте управляемые профили, ограничения kiosk, защиту ОС, TLS и регламент доступа.

Журналы содержат действия/идентификаторы, не пароли или секретные токены. Bootstrap credentials, ключи, .env, import credentials и backup хранятся вне Git и публичного web-root. Контейнер Runtime не получает приватный control/release key.
