# Состояние Kezek — 26.10.2026

Подготовлена публикация исходников в github.com/kazievbeking/kezek: добавлен сценарий INVESTOR-DEMO.md, исключены локальные секреты/данные и исходный пользовательский PDF. Bootstrap создаёт случайные восьмизначные регистрационные коды для новых установок и сохраняет существующие регистрации. Публикация исходников не означает внешнее размещение работающего приложения.

Новая веб-платформа после удаления прежних файлов. Рабочий корень `D:\OSPanel\domains\kezek`. PostgreSQL демонстрации создан отдельно; старые базы не используются. APK/EXE/Electron и мобильных клиентов нет.

## Реализовано

Реализована трёхуровневая структура: Company → CompanyBranch (филиал) → Branch (точка). В каждом филиале создаётся несколько точек. Добавлены отдельные CRUD филиалов в Runtime/Control Plane, выбор «филиал → точка», группировка назначений/регистраций, подписанная активация структуры, отчёты по филиалу и уточнение CSV через companyBranchCode. Очереди, сотрудники и устройства изолированы по конкретной точке, соседние точки того же филиала не расширяют права автоматически. Миграции сохраняют прежние ID и данные. Подробности — BRANCHES-POINTS.md.

Обновлён output/pdf/Kezek_Manual_A-Z_RU.pdf: 34 страницы, 32 раздела с оглавлением/закладками, установка и подключение от А до Я, настоящая структура филиалов и точек и глава о миграции. Сборка — scripts/build-manual.py (ReportLab); проверка — scripts/check-manual.py. Внешнее production-внедрение и аппаратные ограничения обозначены в документе.

Runtime 1.1.0: столы исключены из рабочего процесса и интерфейсов. Администратор назначает услуги/подуслуги сотруднику, смена начинается без стола, FIFO и передачи ограничены его назначениями. Пустой список не даёт допуска к очереди. Дисплей направляет посетителя к сотруднику по имени. Исторические столы и ссылки сохранены; прежние пустые назначения заполнены услугами ранее назначенных столов. Изменение версионировано: Runtime protocol=2, Control Plane protocol=1. Актуальные правила — EMPLOYEE-SERVICES.md; прежние упоминания столов ниже относятся к истории развития.

26.10: добавлены вложенные услуги и подуслуги. Дерево и выбор родителя в админке, пошаговый выбор конечной услуги и навигация на терминале, наследование назначений стола/сотрудника, фильтр отчёта по ветке. Новая миграция сохраняет прежние услуги и талоны, запрещает циклы и связи между филиалами/компаниями. Подробности: SERVICES.md.

В боковом меню администраторов компании/филиала убраны ссылки «Рабочее место», «Терминал» и «Экран очереди»; оставлены административные разделы. Для сотрудников ссылка на рабочее место сохраняется. Отдельные URL терминала, дисплея и рабочего места продолжают работать.

26.10: разделы админки компании перенесены в левую панель. «Обзор» доступен сразу; раскрывающиеся группы: «Организация» (филиалы, услуги, столы, устройства), «Персонал» (сотрудники, импорт), «Аналитика» (отчёты, аудит), «Система» (настройки, обновления). Обновления доступны только COMPANY_ADMIN. Выбранный подпункт хранится в URL, нужная группа раскрывается при загрузке и переходах назад/вперёд.

Разделы Control Plane перенесены из верхних вкладок в левое меню: компании, филиалы, установки, токены, устройства, аудит, обновления, владельцы. Выбранный раздел сохраняется в URL после `#`; поддерживаются обновление страницы и переходы назад/вперёд.

26.10: по запросу убран раздел сотрудников из Control Plane. Runtime больше не отправляет сведения сотрудников даже в managed, Control Plane игнорирует старое поле employees. Новая миграция удаляет ранее сохранённые списки сотрудников из telemetry. Новая удалённая блокировка сотрудников из Control Plane отключена. Учётные записи и управление сотрудниками в админке компании сохранены.

По запросу убраны кнопки «На весь экран» и «Включить звук» с ТВ-дисплея. Звуковой контекст активируется обычным касанием экрана или нажатием клавиши, если браузер требует взаимодействия. Полноэкранный режим задаётся средствами браузера/kiosk.

Дисплей упрощён по запросу: только очередь — вызываемые номера с направлением к столу и ожидающие номера в порядке выдачи. Карточки всех столов, их состояния и история вызовов убраны. DISPLAY получает только публичные номера/статусы/привязку к столу, без сотрудников и их учётных данных.

- Терминал, ТВ и отдельная запись компьютера сотрудника. Постоянная сессия устройства, имя/тип/филиал, привязка к столу, активность, отзыв. Сотрудник, компьютер и стол — разные сущности.

- Табличное редактирование сотрудников, CSV/XLSX: mapping, duplicate policies, preview, ошибки строк, подтверждение, отчёт и индивидуальные пароли только в ответе. Ограничения на ZIP/XLSX и CSV формулы.
- FIFO, конкурентно безопасная выдача/вызов, собственная нумерация филиала/дня/префикса, идемпотентные команды, PostgreSQL-транзакции, transactional outbox. Смены, паузы, вызов/повтор/обслуживание/завершение/неявка/отмена.
- Передача одному свободному сотруднику того же филиала с принятием/отказом/отменой/истечением; номер сохраняется, участие хранится интервалами.
- Терминал: сначала сохранение, затем 80-мм browser print, повторная печать того же талона, возврат к услугам. ТВ: текущие/последние вызовы, часы, подсветка, звук после разрешения пользователя, fullscreen, устаревший снимок при обрыве.
- Polling по умолчанию 1,5 с без наложения запросов, version cursor/backoff; Socket.IO и настоящий HTTP fallback в Auto; повторная синхронизация после подключения. Предложение обновить UI с защитой активного клиента.

- Managed bridge с явным allowlist; isolated без персональной telemetry. Подписанные немедленные/отложенные команды, аудит, receipt от повторов, последнее известное состояние. Технический статус последних обновлений без manifest/секретов.

## Что требует настройки/проверки перед внедрением

1. Внешний хостинг, домен, HTTPS, firewall, supervisor и реальные production-секреты не предоставлены. Сейчас доступны только локальные адреса; после перезагрузки запускать по LOCAL.md.
2. Docker/Compose в этой среде не запускались. Конфигурация подготовлена, но ей нужен deployment rehearsal на выбранном сервере.
3. Нет доступа к приватному GitHub и настоящему каналу релизов. Созданы только локальные dev signing keys. Скачивание реального private release, полный проход установки, миграционный отказ/rollback и восстановление backup на production не выполнялись. `MAINTENANCE_ENABLED=false`; см. UPDATES.md. pg_dump/pg_restore должны быть установлены и совместимы.
4. Физический 80-мм принтер не подключён. Браузер не подтверждает бумагу и не гарантирует silent print. Реальный kiosk, звук/автозапуск и принтер проверяются на оборудовании заказчика.
5. Автоматического сетевого туннеля к изолированной установке нет. Полный административный вход владельца возможен только по доступному, разрешённому Runtime URL и opt-in оператора. Команды отзыва при разрыве ожидают восстановления канала.
6. Для v1 — один API-процесс на Runtime; multi-node Socket.IO потребует общего адаптера. Разные локальные Runtime не объединяют оперативные очереди. Отчётность каждой установки доступна в её админке.
7. Импорт: до 5 МБ, 200 строк, 30 столбцов; разархивированный XLSX до 30 МБ. Логины уникальны в пределах Runtime, а не только компании. Показ истории ограничен 200 сменами/500 интервалами; агрегаты считаются по полной выбранной когорте. Нагрузочные испытания большого клиента ещё не проводились.
8. Часы филиала хранятся как настройки; автоматическое закрытие выдачи по расписанию не реализовано. Набор доступных языков задаётся в настройках компании/филиала. Редактирование устройств сохраняет филиал, перенос выполняется отзывом и новой регистрацией.
9. Браузерная привязка не является аппаратной защитой от клонирования профиля. Администратор локального сервера имеет технический доступ к исходникам и собственной БД; см. PRIVACY.md.

Внедрение на выбранный сервер с проверкой Compose/TLS/backup/restore, подключение реального read-only release channel и rehearsal безопасного обновления, аппаратная проверка киоска/принтера/TV, нагрузочные проверки и постраничная история.
