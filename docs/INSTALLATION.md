# Инструкция установщику: от подготовки до работы

## 1. Серверы

Для каждого backend: Node.js 22+, PostgreSQL 16+ с UTF8, локальный диск под БД/backup и HTTPS reverse proxy для внешнего доступа. Для Docker нужен Docker Engine/Compose. Все браузерные ресурсы поставляются локально; внешние шрифты/CDN не нужны. Для сборки нужны npm-пакеты или заранее подготовленный offline-пакет/образ.

Control Plane можно разместить на вашем VPS. Runtime — на вашем сервере (несколько изолированных компаний) или на сервере заказчика. PHP-only хостинг не исполняет Node.js backend. Статический frontend можно разместить отдельно, но cookie-сессии требуют корректной HTTPS/same-site конфигурации; рекомендуем frontend и его API на одном origin.

## 2. Ключи и отдельные окружения

Вне Git создать два набора Ed25519 ключей: Control Plane для активации/команд и release key для обновлений. Пример с OpenSSL:

```sh
openssl genpkey -algorithm ED25519 -out control-private.pem
openssl pkey -in control-private.pem -pubout -out control-public.pem
openssl genpkey -algorithm ED25519 -out release-private.pem
openssl pkey -in release-private.pem -pubout -out release-public.pem
```

Приватный Control Plane key — только в окружении владельца. Заказчику передаются **только публичные** control/release keys. `.env.runtime.example` и `.env.control.example` описывают раздельные окружения. Общая корневая `.env` предназначена для локальной разработки, не копируется заказчику. Закройте права на конфигурацию и backup средствами ОС.

## 3. Docker

Скопировать `.env.compose.example` → `.env.compose`, `.env.runtime.example` → `.env.runtime`, `.env.control.example` → `.env.control`. Установить **разные** URL-safe пароли двух баз, пути к ключам, origins и секрет установщика (32 случайных байта). Для production `COOKIE_SECURE=true`.

```sh
docker compose --env-file .env.compose up -d --build
docker compose --env-file .env.compose run --rm control node --import tsx scripts/create-owner.ts
```

Команда создания первого владельца требует `OWNER_LOGIN`, `OWNER_PASSWORD` от 12 символов из `.env.control`; если владелец уже существует, команда откажет. Дополнительных владельцев создаёт вошедший владелец во вкладке «Владельцы платформы». После bootstrap убрать OWNER_PASSWORD из постоянного окружения. Не запускать демо-bootstrap на production.

У Control Plane и Runtime независимые базы, тома, migration jobs и backend. В контейнер Runtime не монтируется приватный ключ Control Plane. Для установки только Runtime можно запускать сервисы `runtime-db`, `runtime-migrate`, `runtime` и передать подписанную активацию вручную. Не запускайте второй набор баз на портах уже работающей установки без отдельной конфигурации.

## 4. Домен, сеть, HTTPS

Например `owner.example.kz` → Control Plane:3002 и `queue.example.kz` → Runtime:3001. Настроить A/AAAA, действительные TLS-сертификаты и reverse proxy с WebSocket Upgrade. Разрешить 443; прямые 3001/3002 ограничить firewall, 5432 не публиковать. Origins указываются полностью, без завершающего `/`. Не включать доверие к произвольному X-Forwarded-For. За proxy без настройки доверенной подсети rate limit входа может быть общим для пользователей — настройте конкретный доверенный proxy, а не `trust proxy=true` без ограничений.

Для LAN: фиксированный адрес/DHCP reservation, доступ TCP 3001 только из разрешённой подсети. Предпочтителен внутренний HTTPS с доверенным локальным сертификатом; HTTP допустим только в доверенной изолированной LAN с осознанием передачи паролей/сессий без шифрования. Проверку TLS не отключать.

## 5. Создание заказчика

В Control Plane:

1. «Компании» → добавить название и логин первого администратора.
2. «Филиалы» → добавить код, название, адрес для каждого подразделения.
3. «Установки» → cloud/local, managed/isolated, URL, разрешённые компании и филиалы.
4. Сохранить выданный `bridgeToken` и ID. Bridge token записать только в серверную конфигурацию Runtime, если разрешён обмен. Control Plane хранит его хеш, повторно секрет не показывает.
5. «Токены подключения» → выбрать компанию, установку, филиалы, типы устройств, срок и лимит. Сохранить короткий токен и скачать **подписанный файл активации**.

Для филиала на независимом локальном сервере создать отдельную установку и ограниченный ей токен. Регистрационный лимит действует в данной установке; несколько несвязанных серверов не изображают общий онлайн-счётчик.

## 6. Активация Runtime

Указать INSTALLATION_ID и CONTROL_PUBLIC_KEY_FILE, создать собственный SETUP_SECRET. Открыть `/setup`, ввести секрет установщика и загрузить подписанный JSON. Пакет проверяется локально, Control Plane в этот момент не нужен. Его срок и ID установки должны совпадать. Полученные индивидуальные временные пароли первых администраторов сохранить сейчас; при повторном импорте существующие учётные записи и пароли сохраняются. При первом входе необходима смена пароля.

Обновление набора компаний/филиалов/токенов на изолированном Runtime выполняется новым подписанным пакетом. Применение пакета привилегированно и записывается в аудит. Секрет установщика хранить у ответственного оператора, не на публичном терминале.

## 7. Устройства

На терминале `/terminal`, на ТВ `/display`: токен → название устройства → разрешённый филиал. Браузер запоминает HttpOnly-сессию, связанное устройство, компанию и филиал. После перезагрузки рабочий экран открывается сразу. Повторная регистрация нужна после отзыва/выхода, сброса cookie или профиля браузера. Private/incognito-профили удаляют данные после закрытия и для постоянного киоска не подходят.

Для компьютера сотрудника открыть `/workstation`, зарегистрировать его отдельным токеном с ролью WORKSTATION, затем войти в `/staff` личным логином. Cookie компьютера не заменяет cookie пользователя. Сотрудник может смениться, запись компьютера остаётся.

## 8. Настройка филиала и пользователей

С Runtime 1.1.0 столы не используются. После создания услуг открыть «Персонал → Сотрудники» и назначить каждому филиалы и услуги/подуслуги. Смена начинается без выбора стола. Пустое назначение не даёт доступа к очереди. Текущая инструкция и переход на Runtime protocol=2 — EMPLOYEE-SERVICES.md; прежние описания столов ниже относятся к старой модели.

Для вложенных услуг открыть «Организация» → «Услуги», выбрать «Добавить подуслугу» или родителя в форме. Назначение родительской услуги столу/сотруднику охватывает её потомков; талоны выдаются только для конечных услуг. Подробная инструкция — SERVICES.md.

В `/admin` выбрать доступный филиал. COMPANY_ADMIN видит все филиалы своей компании; BRANCH_ADMIN — назначенные. Настроить услуги с названиями RU/KK/EN и префиксами, столы и несколько услуг на стол, сотрудников и разрешённые филиалы/столы/услуги. Для изменения стола или активных назначений сначала закрыть смену. Блокировка пользователя завершает его сессии; текущий талон не удаляется автоматически. При восстановлении доступа сотрудник продолжает сохранённое обслуживание.

У каждого пользователя отдельный логин (уникальный внутри Runtime). Email необязателен. При создании/сбросе выдаётся индивидуальный временный пароль, видимый только в ответе; в БД — Argon2id. Первый вход обязательно меняет пароль. Существующий владелец платформы не получает универсальный пароль сотрудников.

Общие настройки компании и переопределения филиала находятся в «Настройки». Локализованные названия используют выбранный язык с fallback на русский. Язык сохраняется в браузере и профиле пользователя/устройства.

## 9. Kiosk и печать

Открывать закреплённый URL в полноэкранном профиле браузера. Настройки серверного подключения устройства требуют проверки логина/пароля администратора этой компании с доступом к филиалу. Это защита интерфейса, не администратора ОС.

Печать — `window.print()` с шаблоном 80 мм. Сначала сервер создаёт талон, затем печать. Повторная печать использует тот же талон. Бесшумная печать зависит от администрируемой kiosk-конфигурации браузера; отдельный локальный сервис в проект не входит. Браузер не сообщает надёжно о физическом выходе бумаги и может не отличать отмену диалога. Сообщение «отправлен в браузерную печать» не означает подтверждение оборудования.

На ТВ кнопки звука и полноэкранного режима скрыты. Если браузер блокирует звук, один раз коснуться экрана или нажать клавишу. Полноэкранный режим включать средствами браузера (F11) или kiosk. При обрыве сохраняется последний снимок с предупреждением. Не использовать автоперезагрузку страницы как транспорт обновления.

## 10. Работа сотрудника

Войти личным логином, сменить временный пароль, выбрать разрешённый филиал и стол, начать смену. Вызвать следующего → начать обслуживание → завершить/отметить неявку. Пауза и закрытие смены требуют отсутствия активного клиента. Передача: выбрать работающего свободного получателя внутри филиала → комментарий → запрос. До принятия клиент остаётся у отправителя; отказ/отмена/истечение не перемещают его.

## 11. Диагностика

- Страница не открывается: проверить процессы, DNS, порт, TLS и `/api/health` каждого backend отдельно.
- Runtime работает, Control Plane не видит изменения: проверить режим передачи, BRIDGE_URL/TOKEN, ID, ключ и последнее время синхронизации. Не останавливать очередь из-за недоступной консоли.
- Устройство не подключается: проверить импорт подписанной активации, срок/лимит/тип токена и разрешённый филиал.
- Нет WebSocket: выбрать polling/Auto, проверить Upgrade proxy. Polling по умолчанию не требует сокета.
- Импорт отклонён: посмотреть ошибки каждой строки, назначения, дубликаты, лимиты файла. Не повышать роль импортом.
- Обновление отложено: активный клиент, незавершённое подтверждение печати, время вне окна или MAINTENANCE_ENABLED=false. Подробнее UPDATES.md.
- Забыта бумага/закрыт браузер во время печати: после физической проверки оператор может выполнить `node --env-file=.env --import tsx scripts/clear-print-lease.ts TICKET_UUID`. Действие аудируется; автоматического подтверждения физической печати нет.
